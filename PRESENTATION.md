# Сценарій показу NEXLAB

Цей документ допоможе розповісти викладачці про проєкт і послідовно показати його роботу. Орієнтовна тривалість — 8–12 хвилин. Інтерфейс сайту український, пояснення можна давати російською.

## 1. Короткий вступ — що сказати

> NEXLAB — навчальний вебпроєкт у форматі магазину електронних компонентів і платформи DIY-проєктів. У ньому є каталог, картки товарів, кошик, оформлення замовлення, особистий кабінет, навчальні інструкції та адміністративна панель. Мета проєкту — показати, як взаємодіють інтерфейс, сервер і база даних на прикладі знайомого сценарію інтернет-магазину.

> Це демонстраційна робота для коледжу, а не запущений бізнес. Для показу на комп’ютері сайт, API та база даних працюють локально. Статична версія на GitHub Pages має інше обмеження: GitHub Pages віддає файли сайта, але не запускає Node.js-сервер.

## Концепція роботи

NEXLAB поєднує навчальний каталог електронних компонентів із майстернею DIY-проєктів. Ідея полягає в тому, щоб показати повний шлях від пошуку потрібної деталі до її застосування у практичній збірці. Сайт орієнтований на учнів і початківців, які вивчають електроніку та хочуть знаходити компоненти, інструкції й допомогу в одному місці.

Користувач може шукати товари, переглядати їхні характеристики й наявність, додавати їх до кошика та пройти демонстраційне оформлення замовлення. У розділі DIY-проєктів доступні інструкції зі списками компонентів. Спільнота має окремі вкладки з ідеями, опублікованими збірками та запитаннями до них. Картки акцій формуються з актуальних цін каталогу та доступного перевіреного купона. Реальних платежів у навчальній версії немає.

Для демонстрації важливий не лише інтерфейс магазину, а й зв’язок між його частинами: браузер показує дані та приймає дії користувача, сервер перевіряє важливі операції, а база даних зберігає записи. Адміністративна панель дає змогу показати керування товарами, залишками й демонстраційними замовленнями.

### Як проходить основний сценарій

1. Відвідувач знаходить компонент у каталозі або обирає навчальну ідею.
2. Переглядає інструкцію, список потрібних деталей або збірку іншого учасника.
3. Додає товари до кошика та оформлює демонстраційне замовлення без оплати.
4. За потреби публікує власну збірку чи ставить запитання щодо її коду або підключення.
5. Адміністратор керує демонстраційними даними через захищену за ролями панель.

### Два режими демонстрації

Локально команда `npm start` запускає сайт і Node.js API. Сервер зберігає дані в SQLite на цьому комп’ютері; окремий зовнішній хостинг для показу не потрібен. Це основний режим для повної демонстрації коледжного проєкту.

GitHub Pages публікує статичні файли браузерної частини й сам не запускає Node.js та не надає спільну базу даних. Для спільних онлайн-акаунтів і даних передбачений окремий варіант із Firebase Authentication, Firestore і Cloud Functions, який потрібно попередньо налаштувати.

## 2. Підготовка перед показом

1. Відкрий термінал у папці проєкту `E:\app\NEXLAB`.
2. Переконайся, що встановлено Node.js 24 або новішої версії.
3. Запусти `npm start`.
4. Відкрий `http://127.0.0.1:8767` у браузері.
5. Перевір заздалегідь вхід адміністратора. Його локальні дані задаються у `.env`; не показуй пароль на проекторі й не додавай `.env` до Git.
6. За бажанням покажи GitHub-версію окремою вкладкою, пояснивши, що це статичне розміщення.

Якщо Node.js сервер не запускається, перевір версію `node --version`, а потім — чи не зайнятий порт `8767`.

## 3. Демонстрація сайту — порядок і слова

### Крок 1. Головна сторінка

Покажи головну сторінку та скажи:

> Це стартова сторінка NEXLAB. Звідси можна перейти до каталогу, навчальних проєктів і спільноти. Спільні шапка та підвал формуються кодом, тому повторювані елементи не потрібно окремо підтримувати на кожній сторінці.

### Крок 2. Каталог і товар

Відкрий каталог, скористайся пошуком або фільтром, потім перейди в одну картку товару.

> Каталог показує товари, зображення, ціни й наявність. Сторінки та картки створюються з даних каталогу. Пошук і фільтри допомагають знайти компонент, а сторінка товару показує повніші відомості.

Покажи додавання товару до кошика, обране або порівняння, якщо час дозволяє.

### Крок 3. Кошик і замовлення

Додай товар до кошика, відкрий кошик і сторінку оформлення. Не вводь справжню адресу, телефон чи платіжні дані.

> Кошик дозволяє змінити кількість товарів. Під час оформлення сервер повторно перевіряє товари, ціни й залишки, а потім зберігає замовлення. У локальному режимі дані потрапляють у SQLite. Онлайн-оплата не підключена.

### Крок 4. Проєкти

Відкрий список проєктів і одну інструкцію.

> Проєкти допомагають перейти від каталогу деталей до навчального результату: сторінка містить опис, потрібні компоненти та кроки складання. Це друга частина ідеї сайту — не тільки показати компоненти, а й допомогти застосувати їх на практиці.

### Крок 5. Обліковий запис

Увійди під заздалегідь створеним навчальним користувачем або покажи готовий сеанс.

> Після входу користувач може переглядати власні замовлення, профіль і збережені проєкти. На локальному запуску користувачі та сесії працюють через сервер. На GitHub Pages спільні облікові записи потребують Firebase Authentication.

### Крок 6. Адмінпанель

Відкрий `/admin/index.html` під обліковим записом адміністратора. Покажи розділи меню, каталог товарів, один приклад редагування та замовлення. Для демонстрації не видаляй дані й не змінюй пароль.

> Адмінпанель призначена для керування демонстраційним магазином: перегляду статистики, товарів, залишків, замовлень і користувачів. Доступ перевіряється за роллю на сервері, а не тільки приховуванням кнопок у браузері.

## 4. Як влаштований проєкт

```text
frontend/                 сторінки та код браузера
  *.html                  сторінки: каталог, товар, кошик, проєкти тощо
  js/main.js              запускає потрібну логіку сторінки
  js/                     пошук, кошик, товари, проєкти, акаунт, адмінпанель
  api/                    клієнтські сервіси для API та Firebase
  css/                    загальні стилі й стилі окремих частин сайта
  assets/images/products/ зображення товарів
backend/server/index.js   запускає локальний Node.js-сервер
backend/server/app.js     API, перевірки доступу та робота з SQLite
data/nexlab.sqlite        локальні дані; не додаються до Git
functions/index.js        серверні Firebase-функції для опублікованої версії
firebase/firestore.rules  правила доступу до Firestore
tests/                    автоматичні перевірки
.github/workflows/        автоматична перевірка та публікація GitHub Pages
```

### Ключові файли — одним реченням

- `frontend/index.html` — HTML-каркас головної сторінки.
- `frontend/js/main.js` — точка входу браузерної логіки: завантажує дані та запускає потрібні модулі.
- `frontend/js/products.js` — базові приклади каталогу й проєктів.
- `frontend/js/productService.js` і `frontend/api/productService.js` — завантаження товарів із вибраного джерела даних.
- `frontend/js/cart.js` — локальна логіка кошика в браузері.
- `frontend/js/checkout.js` і `frontend/api/orderService.js` — оформлення та передача замовлення.
- `frontend/js/admin.js` — інтерфейс панелі адміністратора.
- `backend/server/index.js` — налаштування й запуск локального сервера.
- `backend/server/app.js` — серверні маршрути, перевірка запитів і збереження даних.
- `functions/index.js` — Firebase Cloud Functions; GitHub Pages сам їх не запускає.
- `firebase/firestore.rules` — правила, що визначають, хто може читати й змінювати дані Firebase.
- `package.json` — команди проєкту, зокрема `npm start` і `npm test`.
- `README.md` — повна інструкція з запуску й налаштування.

## 5. Як дані проходять через систему

Приклад оформлення замовлення:

```text
Кнопка «Оформити»
  → frontend/js/checkout.js
  → клієнтський сервіс frontend/api/orderService.js
  → локально: /api/... → backend/server/app.js → SQLite
  → GitHub Pages: Firebase callable function → Firestore
```

Локально режим за замовчуванням використовує Node.js і SQLite. На домені GitHub Pages браузер може використовувати Firebase, якщо Firebase налаштований. Дані SQLite з комп’ютера автоматично не синхронізуються з Firebase.

## 6. Технології — коротко

- **HTML** задає структуру сторінок: каталогу, товару, кошика, інструкцій і спільноти.
- **CSS** оформлює сторінки, картки, адаптивну верстку для телефонів і планшетів та світлу/темну теми.
- **JavaScript у форматі ES-модулів** керує пошуком, фільтрами, вкладками спільноти, кошиком, формами й оновленням сторінки без перезавантаження.
- **Node.js** запускає локальний сервер і API, який обробляє запити від браузера.
- **SQLite** зберігає дані локальної демонстрації: каталог, користувачів, замовлення та проєкти.
- **Firebase Authentication, Cloud Firestore і Cloud Functions** забезпечують альтернативний варіант авторизації, спільного сховища та серверної обробки для опублікованої статичної версії.
- **GitHub Actions і GitHub Pages** автоматизують перевірки та публікують браузерні файли сайта.
- **Node.js test runner** запускає автоматичні перевірки командою `npm test`, зокрема сценарії каталогу, спільноти, замовлень і серверних функцій.

## 7. Запитання викладачки — готові відповіді

**Чому потрібен сервер, якщо є HTML?**

HTML і JavaScript працюють у браузері. Сервер потрібен для захисту операцій, перевірки замовлення, ролей і спільного збереження даних. Секрети та довірені перевірки не можна покладати лише на браузер.

**Де зберігаються дані?**

Під час локальної демонстрації — у SQLite-файлі в `data/`. У Firebase-режимі — у Firestore. GitHub Pages сам базу даних не надає.

**Чи можна реально оплатити замовлення?**

Ні. Платіжний провайдер не підключений. Оформлення показує навчальний сценарій, а справжні банківські дані вводити не потрібно.

**Навіщо два варіанти бекенду?**

Локальний сервер дає змогу демонструвати повний цикл без окремого платного хостингу. Firebase дає шлях для спільних даних у статично опублікованому сайті, але його потрібно окремо налаштувати й розгорнути.

**Як перевіряється робота?**

Команда `npm test` запускає автоматичні перевірки сайту, серверної логіки та Firebase-функцій. Перевірки зосереджені на поведінці системи: замовленнях, кошику, доступі, правилах бази та навігації.
