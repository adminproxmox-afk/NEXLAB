# NEXLAB

Каталог електронних компонентів і DIY-проєктів. Для демонстрації в коледжі запускай `npm start`: сайт, API та SQLite працюватимуть разом без Firebase і платного сервера. GitHub Pages розміщує лише статичні файли; для спільних замовлень і облікових записів у майбутньому можна розгорнути цей Node.js сервер або підключити Firebase.

## Структура проєкту

```text
frontend/                 сайт, сторінки та всі браузерні ресурси
  admin/                  панель керування
  api/                    клієнтські сервіси даних та авторизації
  assets/images/products/ фотографії товарів
  css/                    стилі
  guides/                 прошивки для навчальних проєктів
  js/                     логіка інтерфейсу
backend/server/           локальний Node.js API та сервер
firebase/                 правила Firestore
scripts/                  службові скрипти та їхні дані
tests/                    автоматичні перевірки
data/                     локальна SQLite-база (не потрапляє до Git)
```

У корені залишаються лише файли запуску, налаштувань і головна документація. HTML-сторінки зібрані у `frontend/`; workflow публікує саме цю папку. Один раз у GitHub відкрий **Settings → Pages → Build and deployment → Source** і вибери **GitHub Actions**.

## Демо-режим для коледжу

1. Встанови Node.js 24 або новішої версії.
2. У терміналі PowerShell відкрий папку проєкту.
3. Запусти:

   ```powershell
   npm start
   ```

4. Відкрий <http://127.0.0.1:8767>.

Це основний повнофункціональний демо-режим: каталог, кошик, оформлення замовлень, користувачі, адмін-панель, залишки та проєкти працюють через локальний API. Дані зберігаються у `data/nexlab.sqlite` на цьому комп’ютері й не додаються до Git. Firebase та тариф Blaze для такої демонстрації не потрібні.

Не відкривай `frontend/index.html` подвійним кліком: браузер блокує JavaScript-модулі з `file://`.

GitHub Pages може показувати статичний каталог, але самостійно не запускає API та не зберігає спільні замовлення чи акаунти. Якщо потрібна інтерактивна демонстрація за посиланням для всіх пристроїв, розгорни Node.js сервер із постійною базою або налаштуй Firebase.

## Опційно: Firebase для GitHub Pages

Цей розділ потрібен лише якщо хочеш, щоб статична версія на GitHub Pages мала спільні облікові записи, замовлення та склад. Для локальної демо-версії Firebase налаштовувати не потрібно.

GitHub Pages не запускає Node.js, але до нього можна підключити Firebase Authentication, Cloud Firestore і Cloud Functions. У Firebase Console увімкни спосіб входу «Електронна пошта/пароль», створи Firestore та додай домен GitHub Pages до списку дозволених доменів Firebase Authentication.

Зареєструй вебзастосунок у Firebase Console й перенеси його Web config у `frontend/js/firebase-config.js`. Ця конфігурація містить публічні ідентифікатори застосунку; приватний service-account key у браузер не додавай.

Щоб створити адміністратора опублікованого сайту, спершу зареєструй його email через форму сайту. Після `gcloud auth application-default login` виконай `npm run bootstrap:admin --prefix functions -- admin@example.com`. Команда призначить роль `admin` саме цьому наявному Firebase-акаунту; повторний вхід оновить права. Вона не створює пароль і не зберігає секрети в проєкті.

На `localhost` сайт за замовчуванням використовує локальний Node.js API та SQLite, навіть якщо Firebase config уже заповнений. Щоб вручну перевірити Firebase локально, відкрий сторінку з `?backend=firebase`; вибір збережеться у браузері. Поза localhost сайт використовує Firebase, якщо Web config заповнений. Роль адміністратора призначається командою `npm run bootstrap:admin --prefix functions -- <email>` або вручну в `users/{uid}` у Firestore.

### Firebase: захищені замовлення та склад

Оформлення через GitHub Pages запускає callable Cloud Function `createOrder`: сервер сам читає товари, ціни, акційні ціни, купони й комплекти; перевіряє наявність; атомарно списує склад і створює запис у журналі. Ручні коригування складу, статуси замовлень, скасування та приймання фактично отриманих повернень також проходять через сервер. Клієнтські правила забороняють напряму змінювати залишки, створювати замовлення, змінювати їхній статус чи редагувати журнал руху.

Для першого запуску Firebase:

1. Увімкни Cloud Functions і підключи план Blaze з білінгом. Функції працюють у регіоні `europe-west1`; перед підключенням білінгу налаштуй бюджетні сповіщення. Spend caps можуть зупинити функції після досягнення ліміту, але через затримку обліку це не жорстка межа витрат.
2. Встанови Firebase CLI та увійди: `npm install -g firebase-tools`, `firebase login`. Проєкт уже вибраний у `.firebaserc`, тож додавати `--project` не потрібно.
3. У корені проєкту опублікуй Firestore rules і серверні функції: `firebase deploy --only firestore:rules,functions`.
4. Для першого заповнення каталогу на комп’ютері встанови Application Default Credentials через Google Cloud CLI (`gcloud auth application-default login`), потім виконай `npm run seed --prefix functions`. Скрипт додає початкові товари, проєкти, налаштування, демо-купон `NEXLAB10` (10% від 1 000 ₴) та стартові рухи складу; наявні записи не перезаписує.
5. Після цього замовлення на GitHub Pages проходять серверну перевірку. Якщо у Firestore створені власні товари, вони також доступні для замовлення; їхнє поле `stock` є поточним залишком.

Перед демонстрацією GitHub Pages перевір каталог, налаштування, демо-купон і доступність серверного створення замовлень: `npm run check:firebase`. Команда лише читає Firestore та надсилає один неавторизований пробний виклик, який не може створити замовлення чи змінити дані.

Не додавай ключ service account до репозиторію чи браузера. Cloud Functions використовують службову identity Firebase під час виконання. Для функцій Firebase вимагає план Blaze; застосовуються тарифи Google Cloud відповідно до використання.

## Серверні налаштування

Сервер слухає `127.0.0.1:8767` за замовчуванням. При першому запуску скопіюй `.env.example` у `.env`, задай власні `ADMIN_EMAIL` і `ADMIN_PASSWORD` (щонайменше 10 символів) та виконай `npm start`. Сервер створить адміністратора і постійну SQLite-базу `data/nexlab.sqlite`. Файл `.env` і каталог `data` не додаються до Git.

У панелі `/admin/index.html` можна додавати товари, змінювати всі поля картки (назву, категорію, опис, ціну, залишок, бренд, характеристики, теги, ілюстрацію та фото за HTTPS-посиланнями) і видаляти позиції. Часткове оновлення ціни й залишку через API також підтримується. Товари каталогу зберігаються у SQLite та залишаються після перезапуску сервера.

Для відгуків і проєктів спільноти можна вибрати фото з пристрою або додати HTTPS-посилання. Завантажене зображення браузер зменшує до WebP (не більше 220 КБ) і зберігає разом із записом; для навчальної демонстрації це не замінює окреме сховище зображень для комерційного навантаження.

Адміністратор може видати звичайному користувачу тимчасовий пароль у розділі «Користувачі». Новий пароль показується в панелі один раз — передай його власнику облікового запису безпечним способом; після входу користувач має змінити пароль у профілі. Статуси замовлень обмежені допустимими переходами: скасування до відправлення повертає товар на склад, а доставлене замовлення можна позначити поверненим лише після фактичного отримання товару.

Можна змінити `PORT`, `HOST` і `DATA_DIR`. На серверному хостингу встанови `HOST=0.0.0.0`, використовуй порт із `PORT`, а `DATA_DIR` спрямуй на постійне сховище. За HTTPS встанови `SECURE_COOKIES=true` і `PUBLIC_ORIGIN` з повним origin сайта, наприклад `https://shop.example`. GitHub Pages не запускає цей сервер і не підходить для збереження реальних замовлень чи облікових записів.

## Команди

- `npm start` — запустити локальний сайт і API.
- `npm test` — запустити автоматичні тести Node.js.
